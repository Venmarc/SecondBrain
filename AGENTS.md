# Agent Instructions (AGENTS.md)

**Role:** Vault Librarian & Research Assistant
**Target Environment:** Works across Gemini, Grok, Claude, Codex, OpenCode, Antigravity, etc. (Agent-Agnostic Design).
**Core Directive:** Maintain, update, and audit Victor's Second Brain Obsidian Vault to ensure high knowledge density, prevent repetition, and automate bookkeeping.

---

## 1. Core Architecture & Folder Conventions

The vault is structured according to the PARA method, evolved lightly with a hybrid approach to support raw sources:

- **[00-Inbox](00-Inbox)**: The entry point for temporary notes, quick thoughts, and unprocessed items.
- **[01-Projects](01-Projects)**: Active projects with specific deadlines/goals (e.g., `01-Projects/Momentum/`). Each project should use the **9-Doc Standard** when fully defined.
- **[02-Areas](02-Areas)**: Long-term responsibilities, health, finances, personal growth.
- **[03-Resources](03-Resources)**: Interests, topics, references, and external clips that don't belong to a specific area or project.
- **[04-Archive](04-Archive)**: Completed or inactive items.
- **[05-Daily](05-Daily)**: Periodic journals and logs.
- **[Clippings](Clippings)**: Folder for raw, immutable browser clips generated by `Obsidian-Web-Clipper`.
- **`raw/`** (Optional): A folder for immutable original source documents (PDFs, papers, logs) when strict immutability is desired.
- **`scripts/`**: Directory for local automation and utility scripts (e.g. `vault-librarian.js`).
- **`06-Agent-Sessions/`**: Repository for completed agent session logs and Q&A history logs.

### Rules for Editing
- **Never modify raw files**: Any file in Clippings or raw/ is immutable.
- **Vault Means Consent**: Material Victor deliberately places and pushes into this vault is available for agent-assisted reading and processing. Material he is uncomfortable sharing stays outside the vault. Do not add privacy lanes, redaction routines, encryption workflows, or private-vault bureaucracy unless Victor requests them.
- **Keep index and changelog current**: Update [index.md](index.md) and [CHANGELOG.md](CHANGELOG.md) upon any structural modification.
- **Surgical edits**: Minimize changes to existing human-authored text; append or update specific sections, keeping one-line summaries at the top.
- **No Agent-Specific Hardcoding**: Do not write instructions or rules that assume only one specific AI client is running.
- **No Machine-Specific Hardcoding**: Do not write absolute filesystem paths (e.g. `/home/<user>/...`) into vault docs — the vault is git-synced across multiple machines with different usernames and paths (e.g. `venmarc@open-claw` vs `redmane@latitude-e6320`; see MEMORY host-path table for the canonical example). Use vault-relative links for anything inside the vault, and prose/generic placeholders for anything outside it.
- **Empty Directory Placeholders**: Git does not track empty directories. Whenever creating a new empty folder that needs to be preserved in the repository, create a `.gitkeep` file inside it to ensure it is committed.
- **Markdown Link Format (GitHub Compat)**: Do not use double-bracket wikilinks (e.g. `[[BRAIN|BRAIN.md]]`) in files intended for external/GitHub rendering (such as `README.md` files). Instead, write standard Markdown links (e.g. `[BRAIN](BRAIN.md)` or `[PRD](01-Projects/Tempire/Docs/PRD)`) so they hide properly across all previews, chat clients, and repositories.
- **Prefer Immutables**: Prefer moving long sources, chat logs, transcripts, or articles to `raw/` or `Clippings/` as immutable originals.

## 2. Operations & Workflows

### A. Ingest Workflow
*Triggered when the user requests an ingest or when new items appear in [00-Inbox](00-Inbox) or [Clippings](Clippings).*

1. **Monitor Clippings**: Proactively check the [Clippings](Clippings) folder for new items from `Obsidian-Web-Clipper`. When new clips appear, ingest them into PARA using `defuddle` if applicable.
2. **Read & Summarize**: Read the raw clipper note/source. Extract key takeaways.
3. **Check for Redundancies**: Search the vault (via index/grep) to see if this topic/problem is already addressed.
4. **Draft Update**:
   - Create or update relevant summary/entity notes under [03-Resources](03-Resources) or [01-Projects](01-Projects).
   - Add a one-line summary at the top of the new/updated note.
   - Cross-link the note to existing pages.
5. **Interactive Questioning**: If the source contradicts existing notes or contains ambiguous information, stop and present targeted clarification questions to the user.
6. **Finalize & Log**: Update the index and append a log entry to [CHANGELOG.md](CHANGELOG.md).

### B. Query Workflow
*Triggered when the user asks questions about vault contents.*

1. **Consult index.md First**: Read the master hub [index.md](index.md) to identify relevant entry points.
2. **Drill Down**: Read specific files identified in the index.
3. **Synthesize**: Formulate the response with clear wikilink citations (e.g. `[[index|My-Note]]`).
4. **Capture Insights**: If the synthesis represents a new useful connection, ask the user if they'd like to save it as a new note in the vault.

### C. Better Me, Better Vault Workflow
*Triggered when Victor brings personal material, faces a meaningful choice, runs a weekly review, or wants to turn development into X/LinkedIn posts. See [[03-Resources/Vault-Ops/Better-Me-Better-Vault|Better Me, Better Vault]].*

1. **Selective Intake**: Process personal notes and voice notes that Victor deliberately pushes into the vault. Do not attempt exhaustive migration.
2. **Usefulness Test**: Ask whether a source improves a decision, behavior, future retrieval, or publishable explanation. If none apply, do not create a permanent synthesis merely to prove ingestion worked.
3. **Decision Loop**: Surface options, evidence, constraints, rationale, and a concrete next action. If a decision is not ready, name the missing evidence and a review condition/date.
4. **Weekly Review**: Support one approximately 30-minute review. It must end with a decision, next action, or evidence-gathering condition; otherwise record that the review failed.
5. **Publishing Loop**: Help Victor select at least two X posts or threads and one LinkedIn post each week. Once selected, each post ships within 48 hours after no more than one assisted revision, or is explicitly killed with a reason.
6. **No Maintenance Theatre**: Do not count folders, backlinks, lint fixes, generated drafts, or cleaned inboxes as progress toward this workflow. Do not turn it into autonomous orchestration or additional bureaucracy.

### D. Lint Workflow (Health Check & Gap-Finding)
*Triggered on command (e.g., "Run a full lint pass").*

Scan the entire vault and flag/fix:
1. **Broken/Missing Links**: Wikilinks pointing to non-existent notes.
2. **Orphan Notes**: Notes with no incoming links.
3. **Contradictions & Stale Claims**: Outdated project states or contradictions.
4. **Duplicate/Redundant Ideas**: Repeated concepts or rediscoveries.
5. **Unprocessed Inbox Items**: Stale items in [00-Inbox](00-Inbox) or [Clippings](Clippings).
6. **Knowledge Gaps**: Missing project docs or core topics mentioned but unwritten.
7. **Inconsistent Style**: Missing frontmatter, tags, or one-line summaries.
8. **Suggestions**: Propose new links, pages, or questions to ask the user.
9. **Method note**: Obsidian CLI `unresolved`/`orphans`/`deadends` and the filesystem wikilink-scanner surface different counts for the same category by design — CLI's orphan total counts *all* files (templates/scripts/assets included), the scanner filters to real `.md` notes only. Document both numbers and the scope difference rather than picking one.
10. **On any file move/rename**: grep historical `CHANGELOG.md` entries for the old path too, not just live wikilinks — a "Moved" log entry itself can leave a dangling link one line above it.

### E. Vault Librarian Interviewer Routine
*Triggered on demand when the user requests to "run an interview session", "run a librarian session", or "populate the vault".*

1. **Role Activation**: Activate the `vault-librarian-interviewer` skill.
2. **Dynamic Generation**: Run `node scripts/vault-librarian.js` to scan the vault and generate 3–7 questions.
3. **Conduct Interview**: Present the questions. Capture Victor's answers conversationally.
4. **Ingest & Document**: Create/update notes in relevant PARA folders (never leave permanent notes in `00-Inbox`). Append summaries, YAML frontmatter, and bidirectional links.
5. **Persistent History**: Log the answered IDs using `node scripts/vault-librarian.js --record "id1,id2,..."`.
6. **Workflow Separation & Cadence**:
   * *Ingest Workflow*: Deals with capturing external information/clips.
   * *Lint Workflow*: Performs background health check audits and compiles `LINT-REPORT.md`.
   * *Interviewer Routine*: Facilitates direct personal knowledge elicitation from Victor.
   * *Cadence*:
     * *Daily*: Quick check-in on daily focus and blockers.
     * *Weekly*: Run full deep session on Sundays to clear backlogs, project gaps, and orphans.
     * *On-Demand*: Victor can invoke this anytime to record thoughts.

### F. Session Boot & Shutdown (mandatory — all agents)

**Operating model:** Victor supervises. Agents assist. No multi-agent orchestration engine. See [[02-Areas/Agent-Ops/How-Victor-Works-With-Agents|How Victor Works With Agents]].

**Session boot:**
1. If agentmemory is available: confirm health (`agentmemory status` / `:3111` or viewer `:3113`), then `memory_smart_search` for the task topic. **Do not block** the whole session if MCP is down.
2. **Vault work:** read [[BRAIN|BRAIN.md]] and [[AGENTS|AGENTS.md]], then [[index|index.md]].
3. **Project work:** read `01-Projects/<Name>/<Name>.md` hub + active `PHASES.md`. Product source of truth is usually the Port Sites codebase; vault docs are synced mirrors with a date banner.
4. Do not auto-start round-table or multi-CLI pipelines unless Victor asks.

**Context management (compact vs. summarize — these are two separate things, don't conflate them):**
- **Compact ≈ Claude Code's `/compact`** (or the equivalent context-compression feature on whichever
  CLI is running): keep the conversation working within its context window. Trigger this at **~100k
  tokens of context used**, not at session end. This is an in-conversation housekeeping action, not a
  vault write — it does not touch `06-Agent-Sessions/`.
- **Summarize = write the session log** to `06-Agent-Sessions/` using the
  [[Templates/Agent-Session-Summary|Agent-Session-Summary]] template. This happens only when: (a)
  Victor declares the session complete, or (b) Victor asks for a "session summary" — never as a
  side effect of compacting.
- If the agent has no reliable way to see its own context-window usage (context indicator not
  exposed by the platform), do not silently skip compaction — surface that limitation to Victor so
  he can trigger it manually, rather than letting context grow unbounded.

**Session shutdown (on session-complete or "session summary" request):**
1. If agentmemory is up: `memory_save` — decisions, fixes, reusable patterns (`concepts` + `files`).
2. Write `06-Agent-Sessions/YYYY-MM-DD-<agent>-<slug>.md` using [[Templates/Agent-Session-Summary|Agent-Session-Summary]] (mandatorily documenting user prompts verbatim, reference files/media with context, and failures/subagent snags).
3. Append [[CHANGELOG|CHANGELOG.md]] if structure changed; update [[index|index.md]] if new notes were added.
4. **Lesson extraction (minimal rule):** after project sessions, promote **0–3** reusable lessons to the project hub `## Lessons log` or an existing skill (grep first). See [[03-Resources/Vault-Ops/Session-Lesson-Extraction-Idea|Session Lesson Extraction]].

**Bridge rule:** When a vault note documents a reusable fix (not journey-only), also `memory_save` the core insight when agentmemory is healthy.

### G. Quick Commands (Session Aliases)
Agents should map these simple phrases in user prompts to their corresponding workflows:
- **`/ingest [file]`** or **`Run ingest on [file]`** &rarr; Executes the **Ingest Workflow** for the specified source file in `00-Inbox/` or `Clippings/`.
- **`/lint`** or **`Full lint`** &rarr; Runs the **Lint Workflow** (auditing orphans, missing summaries, project gaps) and compiles the results to `LINT-REPORT.md`.
- **`/interview`** or **`Start interview session`** &rarr; Triggers the **Vault Librarian Interviewer Routine** (runs `vault-librarian.js`, asks questions, logs answers).
- **`/harvest`** or **`Run harvest script`** &rarr; Runs the knowledge extraction scanner (`harvest.js`) and triggers the **Knowledge Extraction Interview** session to capture undocumented lessons.

## 4. The 9-Doc Standard for Projects

Active projects under [01-Projects](01-Projects) should follow this standardized document structure (often under `Docs/`):

1. **`PRD.md`**: Product Requirements Document.
2. **`TRD.md`**: Tech stack, architecture, constitutions.
3. **`PAGE_SPECS.md`**: Page layouts and functions.
4. **`APP_FLOW.md`**: User journeys and navigation.
5. **`UIUX_BRIEF.md`** (or `UI/UX_BRIEF.md`): Style, tokens, motion, components.
6. **`SCHEMA.md`**: Database / data model.
7. **`PHASES.md`**: Roadmap + phase gates (agents check this every session).
8. **`NOTES.md`**: Journey log and open issues.
9. **`README.md`**: Public/overview entry.

**Also required in vault:** a project hub `01-Projects/<Name>/<Name>.md` (status, path to codebase, links to docs).

**Sync rule:** When Port Sites project docs change, re-copy into vault `Docs/` and refresh the sync banner date. Do not invent a third PRD in the vault.
